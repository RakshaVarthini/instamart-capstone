# Instamart Customer Intelligence & Support Copilot

## Overview
One repository, four connected Parts, all on synthetic data (generated by `generate_data.py`) and an offline mock LLM (`mock_llm.py`). Both supplied files are committed **unmodified**. No API key, network call or paid service is used. All money is in INR.

| Part | What it does | Main files |
|---|---|---|
| A | Audit, clean and store the raw exports; SQL + pandas analysis | `src/part_a_clean.py`, `src/validate.py`, `sql/queries.sql`, `src/part_a_analysis.py` |
| B | RFM, K-means segments, PCA, lapse model | `src/part_b.py` |
| C | Ticket triage: guardrails, redaction, retries, validation, budget, routing | `src/part_c.py` |
| D | Policy RAG assistant + refund agent (ReAct, safe stopping, resume) | `src/rag.py`, `src/agent.py`, `src/part_d.py` |

Full console output of each step is kept in `reports/*.txt`. Libraries: standard library, pandas, numpy, scikit-learn, joblib (Python 3.12 used; 3.11+ needed).

## Reproduce
```
1. python -m venv .venv
2. source .venv/bin/activate            # Windows: .venv\Scripts\activate
3. pip install -r requirements.txt
4. python generate_data.py              # last line: generated: customers=1200 products=40 orders_raw=13084 tickets=164
5. python src/part_a_clean.py           # audit + clean + CSVs + data/instamart.db
6. python src/validate.py               # prints ALL CHECKPOINTS PASSED
7. python src/part_a_analysis.py        # the 7 SQL queries + pandas cross-check/EDA
8. python src/part_b.py                 # RFM, K-means, PCA, lapse model, outputs/*.csv, outputs/lapse_model.joblib
9. python -m src.part_c                 # triage (needs outputs/customer_segments.csv from step 8)
10. python -m src.part_d                # RAG evaluation, agent scenarios, demos (needs data/instamart.db)
```
`./run_all.sh` runs steps 4–10. Steps 8–10 must run in this order because Part C reads Part B's segment file and Part D reads Part A's database. Seeds: `random_state=42` everywhere, `random.seed(42)` for retry jitter.

### Cleaning rules and what each changed
**Customers**
1. City: strip spaces + title case: 24 spellings → 6 cities (Pune 227, Delhi 210, Bengaluru 197, Chennai 191, Hyderabad 191, Mumbai 184).
2. Gender: 10 spellings + 30 blanks → male 560, female 610, unknown 30.
3. Age: 6 out-of-range values set to missing, then 67 missing ages (61 blank + 6) filled with the city median via `groupby().transform("median")`. Result: 0 missing, range 18–60.
4. `signup_date` converted to datetime.

**Orders** (in this order)
1. `order_ts` converted to datetime.
2. Exact duplicates removed: 13,084 → 12,965 (−119).
3. One record per `order_id`, keeping the latest `order_ts`: 12,965 → 12,309 (−656, all the earlier "pending" records).
4. `order_amount` made numeric; 112 unparseable values (of the 120 raw, 8 sat on rows removed above) refilled with `round(price × quantity × (1 − discount/100), 2)`.
5. Negative delivery_minutes (105 left after de-duplication) set to missing; for completed orders 774 missing delivery times (blank + negative) filled with the median of the order's product category among completed orders (`groupby().transform`). Cancelled orders keep missing delivery_minutes (1,199), since a cancelled order was never delivered and imputing would invent data.

After cleaning: 12,309 rows; 11,110 completed, 1,199 cancelled; 0 missing amounts; completed revenue **INR 2,998,668.80**. Stored as `data/clean/*.csv` and SQLite `data/instamart.db` (tables `customers`, `products`, `orders`; `order_ts` stored as `YYYY-MM-DD HH:MM:SS` text). `src/validate.py` asserts 20 checkpoints and prints `ALL CHECKPOINTS PASSED`.

### K-means (StandardScaler, `n_init=10`, `random_state=42`)
| K | Inertia | Silhouette |
|---|---|---|
| 2 | 1820.8 | 0.465 |
| 3 | 1268.2 | 0.445 |
| 4 | 743.1 | 0.526 |
| 5 | 617.4 | 0.480 |
| 6 | 503.2 | 0.482 |
| 7 | 408.5 | 0.416 |
| 8 | 366.5 | 0.412 |

The elbow is at K=4: inertia drops by 525 from K=3 to K=4 but only 126 from K=4 to K=5, and K=4 has the best silhouette (0.526). Four segments are also a number the business can run four distinct campaigns for. **Final K = 4.** Inertia always falls as K grows (at K = n every point is its own centre and inertia is 0), so K=8 beating K=2 says nothing about quality; it just reflects more centres. Choosing K needs the *rate* of improvement (elbow), cluster separation (silhouette) and interpretability.

### Lapse problem
Cutoff 2025-09-01. Cohort = customers with ≥1 completed order before it: **1,156**; lapsed (no completed order 1–30 Sep) **443 (38.32%)**. Split `test_size=0.2, stratify=y, random_state=42`: 924 train / 232 test. Baseline "never lapsed": accuracy 61.6%, lapsed-class F1 0.
Features (built only from orders before the cutoff plus the customer table): recency_days, frequency, monetary, avg_discount_pct, cancel_rate, avg_delivery_minutes, favourite category, city, age, gender, tenure_days.
**No data from 2025-09-01 onwards entered the features, the segment labels from Part B were not used as features, and no encoder, scaler or resampler saw test rows** (everything is inside a scikit-learn Pipeline fitted on training rows; the oversampler touches the training set only).

### Preprocessing
`ColumnTransformer`: StandardScaler on 8 numeric columns, `OneHotEncoder(drop="first")` on city, gender, favourite category (19 encoded columns). No feature column has a missing value (asserted in code). The scaler's learned mean of frequency is **8.1147** (training rows) versus **8.0285** for the full cohort; they differ because the scaler never sees the 232 test rows, so it estimates the mean from a subset.

### Tuning and test evaluation (lapsed = positive class)
| Model | Best parameters | Best CV F1 |
|---|---|---|
| Logistic regression | C = 100 | 0.6506 |
| Random forest | max_depth = 8, min_samples_leaf = 10 | 0.6811 |

| Test set | Confusion [[TN, FP],[FN, TP]] | Precision | Recall | F1 |
|---|---|---|---|---|
| Baseline | all predicted not lapsed | 0 | 0 | 0 |
| Logistic regression | [[111, 32],[31, 58]] | 0.644 | 0.652 | 0.648 |
| Random forest | [[113, 30],[31, 58]] | 0.659 | 0.652 | 0.655 |

(The logistic best C sits on the edge of the grid; the regularisation strength made little difference.) **Selected model: random forest**, chosen on cross-validated F1 (not on the test set); test F1 0.655 ≥ 0.55. Missing a customer who is about to lapse means losing their future orders with no chance to react, while wrongly targeting a loyal customer costs only a small discount or message. Because the second cost is much lower, a retention team should favour recall; the two tuned models tie on recall (0.652), the forest is slightly better on precision and CV F1, and the oversampling result below shows how recall can be raised further if the team wants a wider net.

### Class-balance experiment (training set only)
Training set oversampled from 354/570 to 570/570 by duplicating lapsed rows (`random_state=42`); best logistic regression refitted; test set unchanged.
| LR | Precision | Recall | F1 |
|---|---|---|---|
| Un-balanced | 0.644 | 0.652 | 0.648 |
| Balanced | 0.589 | 0.854 | 0.697 |

**Recall moved most (+0.20)**; precision fell slightly (−0.06). For the retention team this means catching many more would-be lapsers (76 of 89 instead of 58) at the price of more wrongly targeted loyal customers (53 instead of 32 false alarms), which is attractive when outreach is cheap.

### Interpretation, persistence and retention list
Top-5 random-forest importances: frequency 0.280, monetary 0.271, recency_days 0.115, avg_delivery_minutes 0.061, cancel_rate 0.053. Business reading: how often and how much someone buys dominates, then how recently, and slow deliveries/cancellations add a smaller signal.
Logistic-regression coefficients (standardised features): frequency **−1.70** (frequent buyers lapse less), recency_days **+0.04** (longer gaps lapse more, a weak effect once frequency is known), tenure_days **−0.05** (longer-standing customers lapse slightly less).
The selected model is saved to `outputs/lapse_model.joblib`; reloading it reproduces the original test predictions exactly (checked: True).
`outputs/retention_list.csv`: of 40 Premium customers in the test set, the top 10 by predicted lapse probability (0.452–0.487) are listed; **1 of the 10 truly lapsed**. The retention list is illustrative and not a leakage-free evaluation: the Premium flag comes from whole-window RFM that includes September, the window that defines the lapse label.

## Part C
Pipeline: `src/part_c.py`. Order of operations per ticket: empty check → long check → budget check → redaction → model call with retry → validation. Tickets are processed in file order.

**Input guardrails:** 4 empty tickets (`skipped_empty`) and 4 long tickets (`flagged_long`, 734 estimated tokens each, limit 400) never reach the model.

**Redaction** (email → phone → order id, exact patterns from the brief), across all 164 tickets: 55 emails, 91 phones, 132 order ids, **278** in total; re-applying the patterns to redacted text finds **0**. Every prompt message is asserted PII-free before each call, and the user message is exactly the redacted ticket text.

**Prompts:** zero-shot (24 estimated tokens) and few-shot (110, contains `EXAMPLES:` with four labelled examples including fraud). Both contain CLASSIFY, the four categories and the JSON-only format.

**Retries:** max 3 retries, wait = `0.05 × 2**n × uniform(0.9, 1.15)`, one log line per retry. A full run over the 156 eligible tickets had **19 TransientLLMErrors, all recovered** (every retry was retry number 0; waits 0.0453–0.0562 s; no permanent error).

**Validation** (identical in both runs): 135 `classified_json`, 12 `classified_keyword`, 9 `flagged_invalid_output` (valid JSON with category "shipping", sent to humans, never guessed), plus 4 skipped and 4 flagged long.

### Zero-shot vs few-shot
| Run | Classified | Accuracy | Total tokens | Tokens per classified ticket |
|---|---|---|---|---|
| Zero-shot | 147 | 85.7% (126/147) | 8,152 | 55.5 |
| Few-shot | 147 | 100% (147/147) | 21,568 | 146.7 |

Zero-shot confusion (rows = true, columns = predicted):
| true \ pred | billing | delivery | fraud | technical |
|---|---|---|---|---|
| billing | 38 | 0 | 0 | 0 |
| delivery | 0 | 36 | 0 | 0 |
| fraud | 11 | 0 | 23 | 0 |
| technical | 10 | 0 | 0 | 29 |

The few-shot prompt costs about 91 extra tokens per ticket (2.6× the total tokens) but removed all 21 errors. Those errors matter: 11 were fraud tickets sent to billing, which would miss the high-priority security route and its 2-hour target. The extra tokens are worth paying when a misroute is costly (fraud, premium customers) or volume is modest; for low-risk categories zero-shot at 85.7% may be good enough. Caveat: the mock classifier's behaviour changes with the presence of `EXAMPLES:` (keyword priority order), so the 100% reflects this simulator, and a real model would give different numbers.

## Part D
### RAG
Chunks (40 words, overlap 10): **15** total (refund 4, delivery 3, escalation 3, payment 3, privacy 2). With overlap 0 there are 13. `retrieve(query, k=3)` uses `TfidfVectorizer()` fitted on the chunks and cosine similarity; for "refund policy late delivery" the top three chunks are all from `refund_policy.txt`.
*TF* measures how often a term appears in a chunk, *IDF* how rare it is across chunks (rare terms count more). A limitation: TF-IDF matches words, not meaning, so a question phrased as "reimbursement" would miss text saying "refund".
`answer(question)` sends a system message containing POLICY ASSISTANT and a user message `CONTEXT:\n[file]\nchunk…\nQUESTION:\n<question>`, returning the text and the sources.

| Evaluation | expected_doc in top-3 (of 12) | answer contains expected_fact (of 12) | fallback for unanswerable (of 2) |
|---|---|---|---|
| Chunk 40 / overlap 10 | 12 | 12 | 2 |
| Chunk 40 / overlap 0 | 12 | 10 | 2 |

With overlap 0 two questions break: "What delivery time makes a completed order eligible for a full refund?" (the sentence containing "more than 45 minutes" is cut across a chunk boundary, so the answer returned is the half sentence "receives a full refund of the order amount.") and "How soon is money returned when a payment fails but is deducted?" ("within 48 hours" ended up in a different chunk from the start of the sentence). Overlap keeps boundary-straddling sentences whole in at least one chunk.

As a safety guard, `issue_refund` refuses amounts above INR 1000. `run_agent(...)` implements the ReAct loop (max 6 model calls, token limit 6000, 10 s time limit).

### Crash and resume (S1)
After each tool observation a checkpoint is written to `state/<run_id>.json` (run id, scenario id, full messages, tokens, step, tools executed). A simulated crash was raised right after the second tool; `resume_agent("S1-crash")` continued from the checkpoint. Tools executed across the crash and resume, in order: **get_order → search_policy → calculate_refund → issue_refund** (four executions, none repeated). Final status REFUND, INR 128.25.

### ReAct vs plan-and-execute (≈200 words)
My ReAct agent needs one model call per step plus a final answer: 5 calls (1,002 tokens) for S1, 3 (400) for the cancelled-order S5 and 2 (114) for the unknown order S6. Each call re-sends the growing history, so tokens grow roughly quadratically (S7, six calls, used 3,126). A plan-and-execute design would ask for the full step list once and execute it, so a clean refund would need about 2 calls (plan + summary) and far fewer tokens. This is my analytical estimate; I did not implement it. The cost is rigidity: the plan is made before seeing the order. For S6 (NOT_FOUND) or S5 (cancelled), the later steps would be invalid and a replan call would be needed, while ReAct simply sees the observation and answers in 2–3 calls. For this refund workflow I would choose **ReAct**: the branch points (not found, cancelled, on time, above INR 1000) all depend on tool results, workflows are short (≤5 calls), and money movement benefits from deciding one observed step at a time. A plan-first design would suit long, predictable pipelines where token cost dominates.

## Limitations and Next Steps
- **Retention list is illustrative and not a leakage-free evaluation:** the Premium flag is a post-hoc whole-window label from RFM that includes September, the window defining the lapse label. Only 1 of the 10 listed customers lapsed, which also shows Premium customers rarely lapse here.
- Test set is small (232 rows, 89 lapsers); F1 differences of 0.01 between models are within noise. Logistic regression chose C = 100 at the edge of the grid; a wider grid and cross-validated threshold tuning are next steps.
- Oversampling by duplication can overfit duplicated rows; try class weights or SMOTE-like methods (not allowed here) and calibrate probabilities.
- Data is synthetic: generator archetypes make segments cleaner than real life, and the mock LLM's rules (not a real model) drive the Part C/D accuracy numbers, so they will not transfer to a hosted model.
- `issue_refund` is idempotent only within a run (via checkpoints); across separate runs the same order could be refunded twice. A production version needs a ledger lookup before issuing. The crash demo therefore adds a second S1 entry to the ledger (tagged with its own run id).
- TF-IDF cannot match synonyms; embeddings would help. The 7-day refund window is not enforced because all simulated requests are inside it.
- Next steps: scheduled retraining, monitoring of the triage budget, human review queues with SLAs, and replacing the mock with a hosted model behind the same interface.
